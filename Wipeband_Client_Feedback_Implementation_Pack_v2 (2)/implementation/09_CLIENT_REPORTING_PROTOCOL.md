# Client Feedback Closure / Reporting Protocol

## Truthfulness rule

A user-ready `Action Taken` document must reflect actual implemented changes, not proposed work. Never populate `Implemented & verified` simply because instructions exist. Record exact before/after screenshots/URLs and approval blockers.

## Files to update

- `client-reporting/ACTION_REGISTER.csv`: one record for each source item.
- `client-reporting/CLIENT_ACTION_TAKEN_TEMPLATE.md`: concise client-facing response after execution, ideally grouped into comprehension, purchase, trust/content, media and operations.
- `CHECKPOINT_REPORT.md`: baseline tag and restore notes.
- `IMPLEMENTATION_HANDOFF.md`: tested build/deployment state, commits, affected routes, unresolved claims/assets, test results.

## Suggested status vocabulary

- `Implemented & verified`: code/UI changed and tested in preview or live.
- `Already present & verified`: no change necessary after confirming behavior.
- `Partially implemented`: layout ready; dependent asset/data missing.
- `Blocked - client input`: requires real media, legal facts, testimonials or authorization.
- `Deferred by approval`: client asked to delay/hold functionality.
- `Not done`: explicit remaining defect.

## Reporting structure

1. Acknowledge client's main priority of clarity and easier checkout.
2. Report actual consolidated changes with link to preview/live site.
3. Note what was preserved (responsive design, theme, accessibility, content infrastructure).
4. State exactly what awaits client input, including real video, actual testimonial links/photos, confirmed age, patent/material/returns policy, approved founder story and bundle mechanics.
5. Ask for specific signoffs only if necessary.
6. Keep the row-by-row status register available rather than overwhelming the email.
